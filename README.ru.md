# Bluetooth пропадает после сна: HP Laptop 15s-fq1xxx + Realtek RTL8821CE

<a id="warning"></a>

> [!CAUTION]
> **Прочитай это, прежде чем что-то запускать.**
>
> - Это исправление найдено и проверено **только на одном ноутбуке**: HP 15s-fq1120ur (артикул
>   `286V9EA`), плата DMI **`86C9`**, BIOS **F.30**, система **Arch Linux** с ядром **linux-zen**
>   (7.2.11-zen1) и **systemd**. На других дистрибутивах и ядрах не проверялось. Число `0x06010012` — это номер GPIO-пина
>   чипсета Intel, взятый из *этой* BIOS. На другой модели или другой версии BIOS это же число может
>   означать **другой пин** (тачпад, экран, линии питания — что угодно). Запись не в тот пин может
>   выключить железо до перезагрузки, а в худшем случае привести к последствиям, которые никто не
>   может предсказать.
> - **Сначала проверь модель** (шаг 0 ниже). Если плата, название модели или версия BIOS другие,
>   **ничего не записывай**. Как найти свой пин в своих таблицах ACPI, описано в разделе
>   [Другие ноутбуки](#другие-ноутбуки-как-найти-свой-пин).
> - **Сначала читай, потом пиши.** Команда чтения должна вернуть ровно `0x0` или `0x1`. Любой
>   другой ответ (ошибка, `not called`, большое число) значит, что на твоём ноутбуке такого пина или
>   метода нет: на этом остановись.
> - Хук сделан для **systemd-sleep**. В дистрибутивах без systemd (OpenRC, runit, s6 и т.п.) он
>   сам не запустится: ту же команду нужно вызывать из своего хука пробуждения.
> - `acpi_call` позволяет root вызывать **любой** ACPI-метод. Это мощный отладочный инструмент, а не
>   отполированный драйвер. Опечатка в имени метода или аргументе уходит прямо в прошивку.
> - `acpi_call` — сторонний неподписанный модуль: он помечает ядро как tainted, а при Secure Boot /
>   обязательной подписи модулей может не загрузиться. Это ожидаемо и не является ошибкой этого фикса.
> - Ничего здесь не пишется в BIOS, флеш-память или NVRAM. Состояние пина живёт только до следующей
>   перезагрузки или сна. **Чтобы всё откатить: удали файл хука и перезагрузись.**
> - Автор не связан с HP или Realtek. Никаких гарантий, используешь на свой риск ([MIT](LICENSE)).

Исправление для Linux. На ноутбуках **HP Laptop 15s-fq1xxx** (проверено на **15s-fq1120ur**)
Bluetooth-часть комбо-карты Realtek **RTL8821CE** пропадает после сна в память (S3, `deep`) и
не возвращается до перезагрузки.

**Причина:** при выходе из S3 BIOS не включает обратно линию включения Bluetooth (GPIO-пин
`0x06010012`, на слоте M.2 это `W_DISABLE2#`/BT_EN). Bluetooth-половина чипа остаётся аппаратно
выключенной и исчезает с USB-шины.
**Решение:** хук `systemd-sleep`, который после пробуждения снова поднимает эту линию собственными
ACPI-методами BIOS через модуль `acpi_call`.

## Ручное исправление (голые команды, без скриптов)

Каждый шаг — одна команда, которую можно прочитать и понять. Команды работают в bash, zsh и fish.

**0. Проверь, что ноутбук тот же.** Ожидается: `HP Laptop 15s-fq1xxx`, `86C9`, `F.30`.

```bash
cat /sys/class/dmi/id/product_name /sys/class/dmi/id/board_name /sys/class/dmi/id/bios_version
```

**1. Проверь, что у тебя именно этот баг** (после сна и пробуждения Bluetooth пропал):

```bash
lsusb | grep 0bda:b00a                     # пусто = Bluetooth-адаптер исчез с USB
sudo journalctl -k -b | grep 'usb 1-10'          # ищи "USB disconnect" сразу после "Waking up from system sleep state S3"
```

**2. Установи и загрузи `acpi_call`:**

```bash
sudo pacman -S acpi_call-dkms               # проверено: Arch Linux + linux-zen (для DKMS нужен linux-zen-headers)
                                            # стандартное ядро linux: acpi_call; другие дистрибутивы: acpi-call-dkms (не проверялось)
sudo modprobe acpi_call
```

**3. Прочитай пин включения Bluetooth (только чтение, безопасно):**

```bash
echo '\_SB.GGOV 0x06010012' | sudo tee /proc/acpi/call
sudo cat /proc/acpi/call; echo
```

`0x0` = Bluetooth выключен аппаратно (это и есть баг). `0x1` = включён.
**Любой другой ответ: остановись.**

**4. Включи Bluetooth обратно (только если шаг 3 показал `0x0`):**

```bash
echo '\_SB.SGOV 0x06010012 0x1' | sudo tee /proc/acpi/call
```

Через 1–2 секунды:

```bash
lsusb | grep 0bda:b00a                     # адаптер вернулся
bluetoothctl show                          # контроллер вернулся
```

**5. Сделай это автоматическим после каждого пробуждения.** Создай любым редактором
(`sudo nano ...`) файл `/usr/lib/systemd/system-sleep/bt-en-resume` и вставь в него:

```sh
#!/bin/sh
# /usr/lib/systemd/system-sleep/bt-en-resume
# HP Laptop 15s-fq1xxx (board 86C9, BIOS F.30) + Realtek RTL8821CE.
# After resume from S3 the BIOS leaves the Bluetooth enable line (GPIO pad 0x06010012) low,
# so the Bluetooth half of the chip stays off. This hook raises it again.
# Requires the acpi_call kernel module.

[ "$1" = "post" ] || exit 0
modprobe acpi_call 2>/dev/null
[ -w /proc/acpi/call ] || { logger -t bt-en-resume "no /proc/acpi/call (acpi_call not loaded)"; exit 0; }

printf '%s' '\_SB.GGOV 0x06010012' > /proc/acpi/call
state=$(tr -d '\0' < /proc/acpi/call)

case "$state" in
    0x1) logger -t bt-en-resume "BT_EN already 0x1, nothing to do" ;;
    0x0) printf '%s' '\_SB.SGOV 0x06010012 0x1' > /proc/acpi/call
         logger -t bt-en-resume "BT_EN was 0x0, set to 0x1" ;;
    *)   logger -t bt-en-resume "unexpected answer '$state', not touching anything" ;;
esac
exit 0
```

Сделай его исполняемым:

```bash
sudo chmod 755 /usr/lib/systemd/system-sleep/bt-en-resume
```

**6. Проверь:** усыпи ноутбук, разбуди, затем:

```bash
bluetoothctl show
sudo journalctl -b -t bt-en-resume         # ожидается: "BT_EN was 0x0, set to 0x1"
```

**Откат:**

```bash
sudo rm /usr/lib/systemd/system-sleep/bt-en-resume
```

и перезагрузись. Больше ничего не менялось.

## Симптомы

После пробуждения:

```
$ bluetoothctl show
No default controller available

$ lsusb | grep 0bda:b00a
(пусто)

$ journalctl -k
ACPI: PM: Waking up from system sleep state S3
usb 1-10: USB disconnect, device number 3
```

- Wi‑Fi работает, пропадает только Bluetooth.
- В `rfkill` Bluetooth-устройства нет совсем: оно не заблокировано, а именно отсутствует.
- Перезапуск `bluetooth.service`, перезагрузка `btusb`, сброс USB или PCI ничего не дают.
- Перезагрузка помогает до следующего сна.
- В `/sys/power/mem_sleep` выбран режим `[deep]`.

## Какое железо затронуто

| | Семейство | Точная модель (проверено) |
|---|---|---|
| Ноутбук | HP Laptop 15s-fq1xxx (Intel Ice Lake, 10-е поколение), плата DMI `86C9`, семейство `103C_5335KV HP Notebook` | **HP 15s-fq1120ur**, артикул `286V9EA#ACB`, BIOS **F.30** (07/04/2023) |
| Адаптер | Realtek RTL8821C, драйвер Linux `rtw88` | **RTL8821CE**: Wi‑Fi 5 802.11ac 1x1 по PCIe (`10ec:c821`, подсистема `103c:831a`) + Bluetooth 4.2 по внутреннему USB (`0bda:b00a`) |

Проверено на настоящем цикле сна: после `usb 1-10: USB disconnect` адаптер появляется снова в ту же секунду.
Проверено на **Arch Linux** с ядром **linux-zen** `7.2.11-zen1` и **systemd**, `linux-firmware-realtek 20260916`,
прошивка Bluetooth `0x75b8f098`. На других дистрибутивах, ядрах и системах инициализации не проверялось.

Другие модели HP 15s / 14s / 250 G8 с такой же платой, вероятно, страдают тем же, но номер
пина у них может отличаться. Перед установкой прочитай раздел [Другие ноутбуки](#другие-ноутбуки-как-найти-свой-пин).

## Автоматическая установка (скрипт)

То же, что ручное исправление выше, плюс проверки. Сначала прочитай предупреждение в начале.

1. Установи модуль ядра `acpi_call`:

   ```bash
   sudo pacman -S acpi_call        # стандартное ядро linux
   sudo pacman -S acpi_call-dkms   # linux-zen, linux-lts, свои ядра
   ```

   В других дистрибутивах пакет обычно называется `acpi-call-dkms`.

2. Склонируй репозиторий и установи:

   ```bash
   git clone https://github.com/k0kfjjfkdjf/hp-laptop-15s-fq1xxx-fq1120ur-icelake-realtek-rtl8821c-rtl8821ce-bluetooth-after-suspend-fix.git
   cd hp-laptop-15s-fq1xxx-fq1120ur-icelake-realtek-rtl8821c-rtl8821ce-bluetooth-after-suspend-fix
   sudo ./install.sh
   ```

   Установщик проверит модель ноутбука, работу `acpi_call` и то, что пин читается с нормальным
   значением. Потом он скопирует хук в `/usr/lib/systemd/system-sleep/bt-en-resume`.

   Дополнительно: `sudo ./install.sh --rtw88-tweaks` ещё и отключает энергосбережение драйвера
   Wi‑Fi (`disable_lps_deep`, `disable_aspm`) и USB autosuspend для `btusb`. Для починки Bluetooth
   это **не нужно**, но это лечит ошибки `rtw88_8821ce: firmware failed to leave lps state`, которые
   у многих бывают с этой картой.

3. Проверь:

   ```bash
   systemctl suspend
   # разбуди ноутбук, затем:
   bluetoothctl show
   sudo journalctl -b -t bt-en-resume
   ```

   В журнале должно появиться `BT_EN was 0x0, set to 0x1`, а контроллер должен работать.

## Модуль ядра (экспериментально): без номера пина вообще

> [!WARNING]
> Экспериментально. Модуль собирается без ошибок, но **ещё не проверен на настоящем железе**.
> Не удаляй хук `acpi_call`, пока не увидишь, что модуль сработал после настоящего сна.

Вместо зашитого номера пина здесь доработанная копия драйвера из самого ядра,
`drivers/platform/x86/wireless-hotkey.c` (Linux v7.2). Это драйвер, который и так привязан к
беспроводному устройству HP `HPQ6001`. Добавлено одно: после каждого пробуждения он снова вызывает
**`\_SB.WLBT._STA`** — тот самый метод BIOS, который включает радио при загрузке. Дальше BIOS сама
поднимает нужные GPIO-пины, какие бы номера у них ни были на конкретной модели. Ничего не нужно
искать и настраивать.

- Срабатывает только на `HPQ6001` (HP). На устройствах AMD/Xiaomi/LG, которые обслуживает тот же
  драйвер, ведёт себя точно как стандартный.
- Параметр модуля `resume_fix` (по умолчанию `Y`): `echo N | sudo tee /sys/module/wireless_hotkey/parameters/resume_fix` выключает починку.
- Побочный эффект: `_STA` включает **оба** радио. Если перед сном был включён «режим самолёта»,
  после пробуждения радио включится (так же, как после перезагрузки).
- Ставится через DKMS в `updates/dkms`, поэтому имеет приоритет над модулем из ядра и сам
  пересобирается под новые ядра.
- Пишет в журнал ядра: `sudo journalctl -k -b | grep btfix`.

### `btfix`: переключение между стандартным драйвером, модулем и хуком

`btfix` — текстовое меню. Оно показывает, что активно сейчас (какой `wireless-hotkey` на диске и в
памяти, стоит ли хук), и позволяет переключиться:

```bash
sudo ./btfix --install-command   # один раз: ставит команду btfix в /usr/local/bin
btfix                            # меню (sudo попросит само)
btfix status                     # только состояние
```

Пункты меню: 1) включить модуль btfix · 2) вернуть стандартный `wireless-hotkey` из ядра ·
3) поставить/удалить хук `acpi_call` · 4) применить сейчас без перезагрузки · 5) перезагрузка ·
6) журнал починки за эту загрузку.

Для первой проверки модуля оставь хук установленным: если модуль сработал, хук напишет в журнал
`BT_EN already 0x1, nothing to do` — линия к моменту его запуска уже поднята.

## Как это работает

### Карта — это два устройства

RTL8821CE — карта M.2, внутри одного чипа которой две независимые функции. Каждая подключена к
чипсету своим путём:

```
              Intel Ice Lake PCH                         RTL8821CE (карта M.2)
   ┌────────────────────────────────────┐         ┌───────────────────────────────┐
   │ Корневой порт PCIe 00:1c.0  ───────┼────────►│ Wi‑Fi     PCIe 01:00.0        │
   │                                    │         │           драйвер rtw88_8821ce│
   │ USB xHCI 00:14.0, порт 1-10  ──────┼────────►│ Bluetooth USB 0bda:b00a       │
   │                                    │         │           драйвер btusb+btrtl │
   │ GPIO-пин 0x06010012 (BT_EN)  ──────┼────────►│ W_DISABLE2#: Bluetooth вкл/выкл│
   └────────────────────────────────────┘         └───────────────────────────────┘
```

Главная тут — третья линия. У карт M.2 есть вход «выключить Bluetooth». Когда на линии 0,
Bluetooth-часть чипа удерживается выключенной и даже не появляется на USB. Когда 1, Bluetooth
включается, появляется на USB-порту `1-10`, `btusb` загружает прошивку и появляется `hci0`.

### Кто управляет этой линией

BIOS описывает своё железо для ОС в таблицах ACPI (DSDT/SSDT). Если декомпилировать DSDT этого
ноутбука (`iasl -d DSDT.dat`), там видны два вспомогательных метода, `\_SB.GGOV` (прочитать
значение GPIO) и `\_SB.SGOV` (записать значение GPIO), и три места, где трогается пин `0x06010012`:

**1. При загрузке** беспроводное устройство HP `\_SB.WLBT` (`HPQ6001`) включает Bluetooth:

```asl
Device (WLBT)
{
    Name (_HID, EisaId ("HPQ6001"))
    Method (_STA, 0, NotSerialized)
    {
        ...
        If (((BTDS == One) || (CCDS == One)))
        {
            SGOV (0x06010012, One)      // Bluetooth ВКЛ
        }
```

**2. При нажатии «режима самолёта»** обработчик встроенного контроллера переключает оба радио:

```asl
If (((WBTS == One) & (BTDS == One)))
{
    SGOV (0x06010012, Local0)           // Bluetooth вкл/выкл вместе с Wi‑Fi
}
```

**3. При выходе из S3 — нигде.** Ни `_WAK`, ни какой-либо другой путь пробуждения этот пин не трогает.

### Что происходит во время сна

В S3 (`deep`) почти вся платформа теряет питание, включая настройки GPIO чипсета. При
пробуждении пин возвращается в состояние по умолчанию, то есть в **0**. BIOS многое
восстанавливает, но не этот пин, а `WLBT._STA` выполняется только при загрузке. В итоге:

1. После пробуждения на линии включения Bluetooth 0.
2. Bluetooth-половина RTL8821CE остаётся аппаратно выключенной.
3. Она пропадает с USB-шины (`usb 1-10: USB disconnect`) и больше не появляется.
4. Wi‑Fi подключён по другому пути (PCIe) и нормально оживает.

Это видно напрямую: после неудачного пробуждения
`echo '\_SB.GGOV 0x06010012' > /proc/acpi/call; cat /proc/acpi/call` возвращает `0x0`.

### Что делает исправление

`acpi_call` — модуль ядра, который позволяет root вызывать любые ACPI-методы. Хук
`/usr/lib/systemd/system-sleep/bt-en-resume` запускается после каждого пробуждения (`$1 = post`) и:

1. читает пин через `\_SB.GGOV 0x06010012`;
2. если там не `0x1`, вызывает `\_SB.SGOV 0x06010012 0x1`, то есть делает ровно то же, что BIOS при загрузке;
3. пишет результат в журнал (`sudo journalctl -b -t bt-en-resume`).

Примерно через секунду адаптер появляется на USB, и Bluetooth работает как после холодной
загрузки. Сон остаётся в режиме `deep`, так что лишнего расхода батареи нет.

## Почему обычные способы не помогают

Всё ниже проверено на этом ноутбуке в сломанном состоянии. Все эти способы действуют на шины или
на Wi‑Fi, но не на линию BT_EN, поэтому Bluetooth-часть так и остаётся выключенной.

| Попытка | Результат |
|---|---|
| `systemctl restart bluetooth` | контроллера нет |
| `modprobe -r btusb && modprobe btusb` | драйверу не к чему цепляться: USB-устройства нет |
| `btusb enable_autosuspend=n`, `rtw88_core disable_lps_deep=y`, `rtw88_pci disable_aspm=y` | лечит ошибки LPS у Wi‑Fi, Bluetooth всё равно пропадает |
| Отключение питания USB-порта `1-10` (`usb1-port10/disable`) | на порту ничего нет |
| Отвязка/привязка контроллера xHCI | остальные USB-устройства возвращаются, Bluetooth нет |
| Перезагрузка `rtw88_8821ce` | Wi‑Fi сбрасывается, Bluetooth нет |
| PCI `remove` + `rescan` карты | Wi‑Fi сбрасывается, Bluetooth нет |
| PCIe Secondary Bus Reset, PCIe Link Disable | то же самое |
| D3cold корневого порта | невозможно: на этой платформе нет ACPI power resources, порт доходит только до D3hot |
| **`\_SB.SGOV 0x06010012` 0 → 1** | **Bluetooth вернулся за 1 секунду** |

Похожие отчёты: в 2020 году Realtek выпустил обновление прошивки для «8821C BT broken after S3»
([Ubuntu SRU](https://lists.ubuntu.com/archives/kernel-team/2020-October/114229.html),
[LP#1901129](https://answers.launchpad.net/bugs/1901129)), есть похожий
[баг ядра для RTL8822CE](https://bugzilla.kernel.org/show_bug.cgi?id=210141). На этом HP прошивка
уже свежая, а проблема в BIOS, а не в чипе.

## Скрипт диагностики

`bt-diag.sh` — та самая поэтапная диагностика, с помощью которой нашли этот баг. Он сам
перезапускается через `sudo` и сохраняет лог в `logs/`.

```bash
./bt-diag.sh                      # полная диагностика + по очереди все способы восстановления
./bt-diag.sh --no-fix             # только диагностика
./bt-diag.sh --suspend            # настоящий тест сна через rtcwake (сам проснётся через 20 с)
./bt-diag.sh --suspend s2idle     # то же, временно в режиме s2idle
./bt-diag.sh --suspend --unload all   # выгрузить драйверы перед сном
./bt-diag.sh --bt-gpio [сек]      # опустить BT_EN на N секунд и поднять (исправление вручную)
./bt-diag.sh --chip-reset         # аппаратные сбросы карты: PCI reset, отключение линка, питание слота
./bt-diag.sh --full-cycle [сек]   # всё сразу: выгрузить драйверы, удалить карту, выключить USB-порт,
                                  #   линк PCIe и BT_EN на N секунд, включить и активно искать
./bt-diag.sh --hibernate          # тест гибернации (только если настроен resume)
```

Что он проверяет: модель и BIOS по DMI, наличие устройств на PCI и USB, настройки питания USB,
загруженные модули и их параметры, настройки `modprobe.d`, хуки сна, прошивку Bluetooth, rfkill,
пин BT_EN, готовность к гибернации и журнал ядра вокруг сна и пробуждения.

## Другие ноутбуки: как найти свой пин

Если у тебя другой ноутбук с тем же симптомом (комбо-карта, Bluetooth пропадает после S3, помогает
только перезагрузка), причина может быть той же, но номер пина будет другим.

> ⚠️ Запись в случайный GPIO-пин может выключить другое железо или сбить платформу с толку.
> Используй только тот пин, который твоя DSDT явно использует для Bluetooth.

1. Сохрани и декомпилируй таблицы ACPI:

   ```bash
   sudo pacman -S acpica
   mkdir acpi && cd acpi
   for t in /sys/firmware/acpi/tables/DSDT /sys/firmware/acpi/tables/SSDT*; do
       sudo cat "$t" > "$(basename "$t").dat"
   done
   iasl -d *.dat
   ```

2. Найди код, который переключает Bluetooth:

   ```bash
   grep -n 'Device (WLBT)' -A40 *.dsl     # беспроводное устройство HP: вызовы SGOV внутри _STA
   grep -n 'BTRK\|GBTR\|BTDS\|WBTS' *.dsl  # RF-kill Bluetooth из эталона Intel и флаги BT у HP
   ```

   На ноутбуках HP пин, который используется вместе с `BTDS`/`WBTS`, и есть включение Bluetooth.
   Во многих эталонных платформах Intel есть ещё метод `\_SB.BTRK` (пишет в пин `GBTK`).
   *Важно:* на этом ноутбуке `BTRK` есть, но HP использует не его.

3. Проверь значение после неудачного пробуждения и включи:

   ```bash
   sudo modprobe acpi_call
   echo '\_SB.GGOV 0xТВОЙ_ПИН' | sudo tee /proc/acpi/call; sudo cat /proc/acpi/call
   echo '\_SB.SGOV 0xТВОЙ_ПИН 0x1' | sudo tee /proc/acpi/call
   ```

4. Если Bluetooth вернулся, замени `0x06010012` на свой пин в `bt-en-resume` и `install.sh`.

## Удаление

```bash
sudo ./uninstall.sh
```

Удаляет хук и `/etc/modprobe.d/rtl8821ce-fix.conf` (если ставили с `--rtw88-tweaks`).

## Оговорки

- Исправление зависит от `acpi_call`. Если модуля нет (пакет удалён, DKMS не собрался под новое
  ядро), хук ничего не делает и пишет в журнал `no /proc/acpi/call`.
- Номер пина взят из BIOS **F.30**. После обновления BIOS проверь, что `./bt-diag.sh --no-fix`
  по-прежнему показывает линию BT_EN с нормальным значением (`0x1`, пока Bluetooth работает).
- Непроверенные альтернативы: режим `s2idle` вместо `deep` (`mem_sleep_default=s2idle`) должен
  обходить путь пробуждения через BIOS, но во сне тратит больше батареи. Двойное нажатие «режима
  самолёта» после пробуждения тоже должно возвращать Bluetooth, потому что BIOS переключает тот же пин.
